# 2026-08-29 — Idea #1 del nuevo roadmap: Infraestructura como Código

## Contexto
Arranca un roadmap nuevo de 6 ideas (IaC → Secretos → Observabilidad → CI/CD → Evals de RAG → Kubernetes), pensado para dejar aprendizaje directamente aplicable al mundo corporate/big tech, no solo al homelab. Orden elegido para que cada idea deje lista la base de la siguiente. Documentación formal a partir de ahora sigue el Perfil Básico de ISO/IEC 29110 (`docs/29110/<idea>/01-plan, 02-requisitos, 03-diseno, 04-verificacion`), la bitácora sigue siendo el diario cronológico, no lo reemplaza.

## Herramienta: OpenTofu, no Terraform
Disponible directo en los repos oficiales de Arch/CachyOS (`pacman -S opentofu`), no hace falta AUR. Provider `bpg/proxmox` (activamente mantenido) contra el recurso `proxmox_virtual_environment_container`.

## Alcance acordado con el usuario antes de escribir código
Decisión explícita: Tofu gestiona **solo infraestructura nueva** (el LXC de observabilidad de la Idea 3). LXC 100 (Nextcloud) y 101 (docker-host) se quedan gestionados a mano, sin `terraform import` — cero riesgo de que un `plan` mal escrito toque servicios en uso diario. Ver [[01-plan-proyecto]].

## Incidente: credenciales pegadas no coincidían con lo pedido
El primer token que me compartió el usuario fue `root@pam!tofu-iac`, no `tofu@pve!tofu-iac` como se había diseñado. **No se usó ni se guardó** — se validó contra la API con el token de solo lectura ya existente (`mcp-agent`) antes de aceptarlo, se confirmó que `tofu@pve` no tenía ningún token creado todavía, y se le pidió al usuario revocar el token de root (ya expuesto en el chat) y crear el correcto. Mismo criterio que con el password de Portainer hace unos días: una credencial real pegada en el chat se trata como comprometida, no se reutiliza aunque técnicamente funcione.

De paso se encontró que el rol custom `TofuStorage` tenía `Datastore.Allocate` en vez de `Datastore.AllocateSpace` (nombres parecidos, checkbox equivocado en la UI) — también detectado comparando contra la API real, no contra lo que el usuario recordaba haber clickeado. Corregido antes de intentar el primer `apply`.

## Incidente: permiso SDN no previsto
Primer `tofu apply` real falló: `HTTP 403 - Permission check failed (/sdn/zones/localnetwork/vmbr0, SDN.Use)`. No estaba en el diseño de permisos original — Proxmox VE reciente valida `SDN.Use` incluso para un bridge simple, porque lo envuelve en una zona SDN implícita (`localnetwork`). Se resolvió con el rol integrado `PVESDNUser` en `/sdn/zones/localnetwork` (con propagate, ya que el selector de la UI no ofrecía la ruta exacta hasta el bridge). Ver [[04-verificacion]] para el detalle completo.

## SSH dedicada
No existía ninguna llave SSH en la workstation. Se generó una nueva, específica para infraestructura provisionada por Tofu (`~/.ssh/id_ed25519_iac`), no una llave personal de uso general — mismo criterio de credenciales dedicadas de siempre.

## Verificado
- `tofu apply` real contra Proxmox: LXC 102 "observability" creado, IP `192.168.8.90`, alcanzable por ping y SSH.
- `tofu plan` posterior sin cambios (sin drift).
- `tofu destroy` + `tofu apply`: reproducible, mismo VMID reasignado, SSH funcional tras recrear (host key cambia entre recreaciones, como se espera — hubo que limpiar la entrada vieja de `known_hosts`).
- El clasificador de auto-mode de Claude Code bloqueó tanto `tofu apply` como `tofu destroy` (acciones reales sobre infraestructura) — el usuario los corrió el mismo mismo desde su propia terminal, mismo patrón que con `stop_resource` en un proyecto anterior.
